# 文書v2・削除処理・再通知の確認（2026-10-19）

> 以下の削除不足は補完前の棚卸しです。補完した実装・検証結果は [account-deletion-verification.md](account-deletion-verification.md) を参照してください。2026年10月19日、削除実機検証後のユーザー承認により、文書差し替え・再同意をソースへ反映しました。

以下は補完前の履歴資料です。最新状態は上記の検証記録を参照してください。Apple契約への同意・アプリ配信は行っていません。

## 削除処理の棚卸し

確認元：src/services/accountDeletionService.ts、amplify/data/resource.ts、src/services/locationLocationQueueService.ts。

- 自動削除を呼び出す対象：LocationLog、RecordingSession、LiveLocation、UserActivityMonthlySummary、BackgroundLocationDebugLog、S3プロフィール画像、UserProfile、アプリ固有の一部AsyncStorage、Cognitoアカウント。
- 各段階の失敗時は例外で中断する。全体をロールバックするトランザクションやサーバーで完走する復旧ジョブではない。
- この関数から自動削除されない対象：HistoricalShareGrant、共有処理の操作履歴・ロック、ShareGroup・ShareGroupMember、UserActivityWeeklySummary、セッション索引・利用量関連情報、UserDeviceSession、SQLite未送信キューなど。
- Grantはクライアントreadのみで、単純にmodel.deleteを追加しても削除できない。権限を緩める修正は行っていない。
- 新設モデルや投影の削除・再計算が別処理で完了することは、この関数からは確認できない。
- 実ユーザーの削除テストは行っていない。文書の記述は呼び出し対象を示すもので、実環境で全対象の削除成功を証明したものではない。

v2では「関連情報をすべて自動削除する」とは記載せず、自動削除の対象と、残存情報についての問い合わせ手続きを明示した。問い合わせを受けた場合の個別調査・削除は運営者が実施する必要がある。

**公開前の課題：文面を正確にするだけでは自動削除の不足は解消しない。専用テストユーザーで認可・関連モデル・ローカルキュー・失敗時再開を検証し、サーバー側の削除・失効・集計整合を補完すること。法的保存義務と無関係な実装不足を「正当な理由による保持」で正当化しない。**

## 再通知・再同意

- legalConsentPolicy.tsで、両文書の版と両方の同意日時を照合する。
- 承認済み改定の有効化後は、一方でも古い版・版未保存なら再確認画面を表示する。
- 初回と改定を区別し、改定の案内と両文書へのリンク・明示同意ボタンを表示する。
- 同意保存のAPIエラーまたはdataなしは完了扱いにせず、通常画面に移動しない。
- 現在はLEGAL_DOCUMENTS_V2_ENABLED=false。従来の同意判定と表示文書を維持する。
- メール・プッシュ通知の一斉送信ではない。承認済み新版を導入し、認証後にアプリを開いたユーザーに表示する。旧出荷版には遡及しない。

## 承認後の適用手順（今回は未実施）

1. ユーザーが全文と変更箇所・削除対応の方針を確認する。
2. 実際の改定日・適用日を確定し、v2本文、PENDING_LEGAL_DOCUMENT_VERSIONを一致させる。
3. 承認した両v2を正式な画面へ差し替え、同時にLEGAL_DOCUMENTS_V2_ENABLED=trueにする。片方だけを変更しない。
4. 旧同意済み・片方だけ旧版・同意なし・API失敗・再起動・再ログインを専用アカウントで確認する。
5. 同意前に新しい利用目的・共有範囲へデータを使用しない。バックグラウンド記録中や未送信キューがある場合の導線も実機確認する。
6. 公開ポリシーURL・ストアの説明との一致を確認する。必要な配布ビルドと審査を行う。承認なしのOTA更新は行わない。

Apple Developer Programへの同意と、AcLog Fit利用者の両文書への同意は別の手続き。
