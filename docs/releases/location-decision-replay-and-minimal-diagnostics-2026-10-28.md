# 採否順序のオフライン再現と最小診断

2026-10-28。端末・本番データは変更せず、追加ビルド・OTA配信なし。診断コードはローカル変更のみ、既定OFF。採否条件・距離計算・SQLiteスキーマ・本番APIは変更していない。

## 1. 実処理の再生方法と限界

`scripts/diagnostics/locationDecisionReplay.ts` はTypeScript ASTから、現行の次の関数本体を取り出して実行する。React／SQLite／AWSを起動しない。

- 前面：useForegroundLocationRecorderのshouldSaveLocation。
- 背景直接：backgroundLocationTaskのshouldSaveLocation、および実際の精度／速度／重複関数。
- 再送：locationQueueUploadServiceのevaluateQueueLocationSkipReason。
- 基準地点：実際のselectAcceptedBaseline。共通基準は確定成功後だけ新しい時刻へ進めるモデル。

前面・背景状態のマージ、過去の採用SQLite地点、未来の基準を除く選択もモデル化した。ただし保存済み地点しか残っていないため、未採用の全受信点、実際のロック取得順序、待機・タイムアウト後の完了、強制保存、上限制御を含む当時の処理を完全再現するものではない。Cloud createdAt順は採否実行順序ではなく、比較用の仮説にすぎない。背景sourceだけではNative受信箱経由と直接経路を区別できないため、両方の仮説を比較した。

|記録・入力順仮説|背景経路仮説|採用相当地点|再計算距離|
|---|---|---:|---:|
|R1 測位時刻順|再送／直接（同じ結果）|164/210|9171.49m|

この再生は既存保存点に仮説条件を重ねたもの。採用地点数が実記録と一致しないことは、そのまま保存バグの証明にはならない。実行時の基準履歴や入力列が不足していることを示す。いずれの仮説でも異常距離は大きく残り、順序整合だけで静置揺れを解決できたとはいえない。

### 再現できた条件

1. 前面は短時間の大きな変化が距離条件を満たすと採用候補となる。同じ点を再送側へ渡すと、200km/hチェックで除外される条件がある。
2. 新しい共通基準しか残っていない状態で古い地点が遅着すると、selectAcceptedBaselineは未来点を除くため過去基準がnullになる。再送側は基準なしの場合を初回点として扱う。この状態では速度比較が成立しない。
3. これは旧オフライン点を未来の地点に対して誤除外しないための動作でもある。nullを一律エラー／削除に変えると正当な未送信データを失うため、その修正はしていない。

R1/R2で実際に2が起きたかは未確定。次の診断で基準nullの理由と前後の経路を確認する。全経路共通の静置除外閾値は未採用。

## 2. ローカルに追加した観測

`locationDecisionDiagnosticCore.ts` と `locationDecisionDiagnosticService.ts` を追加した。サービス内の定数ENABLE_LOCATION_DECISION_DIAGNOSTICS=falseで無効。保存値・管理者role・リモート設定で有効化できない。現在端末で新しい情報を取れているわけではない。

|追加箇所|観測内容|
|---|---|
|前面保存入口|座標・測位時刻・JS観測時刻・速度・精度・forceSave|
|前面の既存早期returnとロック後判定|実際の基準座標／時刻、前面処理中・重複・保存条件、採用候補かどうか|
|Native受信箱→JS SQLiteの受渡し直前|元のNative行ID、JSが受け取った座標／時刻、所有者／セッション、速度等の存在する項目|
|背景直接保存|精度による除外、ロック後の実基準、速度／重複／保存条件の除外理由|
|SQLite再送|実際に選択した基準、既存評価関数の返却理由、既存received_at、地点ID|
|共通Cloud書込|地点ID、明示失敗／確定新規保存／既存点の確定応答|
|既存Headless診断出力|有効時のみLOCATION DECISION EVIDENCE欄を追加|

共通のcorrelationKeyは所有者・セッション・測位時刻・正確な緯度経度から作り、別経路の同じ点を結び付ける。runtimeIdとsequenceは同じJSランタイム内の観測順を表し、複数ランタイムの完全順序を保証しない。基準点IDを保持していない箇所は座標・時刻で記録し、存在しないIDを作らない。

選択後の基準だけでなく、選択前の共通基準・前面／背景候補・採用済みSQLiteの直前点・処理中バッチの候補も、その経路で実際に取得済みの範囲で最大5件記録する。候補が未来かも記録し、基準nullが「本当に初回」なのか「未来候補しかない」のかを区別できるようにする。診断のための追加DB照会はしない。

「eligible-before-plan-reservation」は品質／保存条件を通過した候補であり、上限予約・ネットワーク保存成功を意味しない。Cloud結果がない場合は失敗や未保存と決めつけず結果不明として扱う。通信例外・ロック取得失敗・上限制御の全分岐を網羅した完全トレースではない。

### 保存処理へ影響を持たせない仕組み

- OFF時は値を組み立てる関数も実行せず、診断用ストレージI/Oなし。
- ON時も診断にawaitせず、独立したAsyncStorageキーへ保存。既存SQLiteテーブルや未送信キューを使用しない。
- 最大1024件、保守的なUTF-8換算512KiB上限。書込は1本にまとめ、待ち中は最新状態へ集約する。破棄数・書込失敗数を記録する。
- 入力値をコピーし、後から元の座標・基準オブジェクトが変わっても診断値が変わらない。
- 診断の値取得例外・ストレージ例外は録画／保存／再送へ伝播させない。採否結果を返すAPIではなく、診断結果は本来の採否に使わない。
- 座標と内部所有者／セッションはローカル診断だけに保持し、自動アップロードしない。パスワード・トークン・email・任意の例外オブジェクトは記録しない。明示した文字列項目は256文字で上限を設ける。
- ON時のCPU／I/O負荷・実機保持は未検証。既定OFFの単体テストが実機ON時の無影響を保証するものではない。診断は調査終了後に削除できる独立したコード。

## 3. 既存で取得できる情報／変更が必要な情報

|項目|取得可否・追加方法|
|---|---|
|現在のJS座標、timestamp、accuracy、speed|既存LocationObjectから観測可能。今回ローカル観測を追加|
|SQLiteのreceived_at、採用基準、理由、地点ID|既存変数から観測可能。今回ローカル観測を追加|
|Native受信箱の行ID／payload|既存Native APIの受渡しで観測可能。今回JS受渡し地点の観測を追加|
|実際のCloud確認応答|既存の書込結果から観測可能。今回追加。タイムアウト後の不明結果は成功と扱わない|
|hasSpeed／hasSpeedAccuracy／速度精度|標準Expo変換では欠落。Native変更が必要。今回は未実装|
|測位elapsedRealtimeNanos／Native受信elapsedRealtimeNanos|標準JSペイロードにない。Native変更が必要。今回は未実装|
|provider／hasAccuracy／mock、GNSSの詳細|標準JSペイロードでは不足。Nativeで最小項目を追加する必要。今回は未実装。providerだけでGNSS／Wi-Fiの内訳を断定しない|

speed=0でも有効性フラグを失っているため、speedValidity=not_exposedと記録。速度精度や単調時刻はnullのまま保持し、値を推測しない。診断を有効化してもこれらNative項目は追加取得できない。

JSの既存項目の観測追加でも、インストール済みアプリへ新コードを届けるには更新手段が必要。現在の追加ビルド・配信禁止下では端末に反映しない。Native不足はOTAだけでも補えない。

## 4. 次の検証手順

### 現時点で行うこと

- オフライン再生、診断OFF／例外／容量上限、既存受信箱・再送・基準キャッシュのテストまでをローカルで実行。
- 両端末は自動記録・共有停止のまま充電してよい。ログアウト、削除、追加待機、再インストール、新規記録は不要。

### 将来、診断を有効にした隔離検証環境を用意できる場合の試験案（未開始）

1. 専用所有者・セッションだけで行い、保存済み件数・未送信状態を事前比較する。採否条件は変更しない。
2. 同じ屋内の机で前面約3分を記録・保存し、すぐ診断を出力。件数・correlationKey・基準・Cloud結果の接続を確認。evictedや書込失敗があれば欠測を明記する。
3. 別セッションで同じ場所のロック背景約3分を記録し、停止保存後すぐ出力する。途中の充電・解除等を記録する。初回は観測の完全性を確認し、いきなり75分待機をしない。
4. JS受信時点で既に飛ぶのか、元payloadとSQLite／保存地点が違うのか、基準nullや未来基準・遅着があるかを判定する。
5. 異常点が再現しなければ、単に静置時間を増やさず、必要なNative情報を取る試験の要否を判断する。屋内／屋外、他のAndroid機種等の比較は一条件ずつ行う。
6. 除外候補ができた後に低速歩行・小周回・折返し・途中停止・通常ランニングを観測モードで比較。採用地点を減らす実保存フィルターはまだ有効化しない。

Native情報が必要な場合は別途変更案を提示する。現在は追加ビルド・配信を実施しない。
